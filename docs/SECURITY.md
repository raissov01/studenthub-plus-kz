# Server security audit

Generated by `cd backend && go run ./cmd/routes > ../docs/SECURITY.md`. The inventory walks the exact
runtime registrations, including the fallback; tests reject undocumented routes, obsolete
entries, and document drift. GET also accepts HEAD through Go's ServeMux.

“signed-in” means student, ambassador, university_staff, employer or admin. Membership,
consent, age, ownership and university restrictions still apply. “employer” means an
employer_members relationship, not merely the users.role value. A “no” in validation on a
read/action with no parameters means there is no application input to validate; authentication
is listed separately. Rate limits are shared Postgres counters, with an in-memory fallback
when Postgres is unavailable. All browser writes use auth.Write (allowed Origin/Referer,
per-IP and per-user budget); /api/client-errors also has a fixed 5/IP/minute budget.
“moderator” is a scoped admin right (admin_grants, granted and revoked only by an admin with a reason,
audited) re-read with the session on every request; it opens the moderation endpoints, never user
management, exports, shop money or role-granting queue kinds (ambassador, mentor, employer verification,
club leader). A blocked account (user_blocks) gets 403 account_restricted from auth.Write on every write
except sign-in/out, password and email settings, DELETE /api/me and the anonymous analytics/error beacons.

The write-guard exceptions are POST /api/telegram and POST /api/cafe/kaspi/webhook: a
constant-time shared-secret check (Telegram's webhook secret; the kaspi-pos sidecar's HMAC-SHA256
signature over the raw body) replaces browser origin/rate checks. All GET cron endpoints mutate data,
but accept only a nonempty CRON_SECRET bearer token and record successful completion.
Tests reject missing/wrong secrets and ensure failed attempts do not advance cron state.

Findings fixed: analytics ingestion lacked the shared origin guard; chat used a separate
write policy. Both now pass through auth.Write. Account deletion used to swallow disk
removal errors; it now refuses to report success while a photo cannot be deleted.
The new settings, error and cron tables have RLS enabled and no app_user privileges.
Error storage uses constant diagnostics/categories, static screen names and browser major
versions: arbitrary names, IDs, tokens, full URLs, IPs and free-form details are not persisted.

Scope: Go API only. Existing feature tests cover student/company/university isolation;
the launch tests add router-wide write/role/switch checks, populated catalog-driven account
deletion, settings and monitoring integration tests. Frontend XSS/CSP, browser scenarios,
PWA and repository-history secret scanning are outside this server-only assignment.
Session signing/cookie settings and Telegram/cron secret checks remain covered by auth/bot tests.
Local market files are removed before the SQL commit: retries are idempotent, but a later
transaction failure can leave a surviving database row without its already-removed photo.
The API assumes the trusted reverse proxy overwrites client IP forwarding headers.
Quiz live games use the only WebSocket route, GET /api/quiz/live/ws: Vercel rewrites do not
proxy WebSockets, so browsers connect to the API origin directly, where the site's cookies do
not exist. The socket therefore accepts no cookie at all: it requires a signed 2-minute join
token (HMAC with a key derived from SESSION_SECRET, separate from session cookies) issued by
POST /api/quiz/live/join or /sessions over normal HTTPS, and an Origin in ALLOWED_HOSTS.
Unlisted quizzes are readable by their 10-character share code (about 57 bits); answer keys
are never part of a play view and live in a separate owner-only RLS table.
Points (FEATURE_POINTS): coins are never cash and never move between students. Every balance
change is a coin_ledger row written by the server in the same transaction as the cached
balance (wallet row locked FOR UPDATE, CHECK coins >= 0, append-only trigger); one action pays
once (unique user/reason/ref), with per-reason and daily caps. Client-sent amounts do not exist:
the API takes only an action id, a reward id and an idempotency key.
Café (FEATURE_CAFE): money never passes through Student Hub. A Kaspi QR is issued in the café's own
name through the café's cashier session (kaspi-pos sidecar, internal network, X-Internal-Api-Key);
the session is stored AES-256-GCM encrypted and app_user cannot read it. Order totals are recomputed
from cafe_menu_items; a client total is ignored. Students read only their own orders and staff only
their café's orders through RLS; every order change is an append-only cafe_order_events row.
Print shop (FEATURE_PRINT, docs/print.md): the same money rule and the café's Kaspi sidecar, with each
shop's own cashier session in print_kaspi_sessions; the sidecar's single webhook reaches print jobs through
the café endpoint (shopkit.RegisterOperations). Uploads are checked by magic bytes (PDF, JPEG, PNG,
DOCX/XLSX/PPTX without macros), 20 MB each, per-student daily file and byte quotas; files get random
names, are never public and are served only through 5-minute HMAC links bound to the file and the viewer
(re-checked at serve time) as attachments with a sandboxing CSP; their bytes are deleted after the shop's
retention period. No antivirus runs: the risk is documented in docs/print.md. Prices are recomputed from
print_services/print_goods; a page count the server cannot make (Office files) is declared by the student
and confirmed or changed by the operator, and a changed price needs the student's approval.
University voice (FEATURE_SURVEYS / FEEDBACK / WELLBEING, docs/UNIVOICE.md): anonymous survey
answers have no user column and no timestamp; double voting is stopped by an HMAC(user id) marker
keyed from SESSION_SECRET in a separate table. Results and CSV are aggregates with every group
under 5 hidden (complementary suppression in breakdowns). Anonymous feedback tickets have no author
(CHECK); the sender keeps a 256-bit device token whose SHA-256 is stored, so the token-holding
routes are callable without a session. Flagged (threat/profanity) tickets are held for admins.
